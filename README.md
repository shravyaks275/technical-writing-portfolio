# My Documentation Approach

Good technical documentation should do more than describe what software does.

It should help the reader **understand, use, troubleshoot, or extend it**.

For each project, I follow a documentation process built around the actual implementation:

### 01 — Understand

Study the application's purpose, architecture, workflows, dependencies, and target audience.

### 02 — Investigate

Review the source code, APIs, configuration, database interactions, technical components, and existing project documentation.

### 03 — Structure

Organize information according to what the reader needs to accomplish rather than simply following the structure of the codebase.

### 04 — Document

Write clear explanations, workflows, references, setup instructions, examples, and troubleshooting guidance.

### 05 — Verify

Cross-check the documentation against the implementation to reduce outdated or inaccurate information.

> **The goal is documentation that developers can actually use — not documentation that simply looks complete.**

# Documentation Principles

I aim to make every document:

**Clear** — Technical concepts are explained in straightforward language.

**Accurate** — Documentation reflects the actual implementation.

**Structured** — Information is organized so readers can quickly find what they need.

**Practical** — Instructions focus on what the reader needs to accomplish.

**Maintainable** — Documents are structured so they can evolve alongside the software.

**Audience-focused** — Developer documentation, API references, and user guides are written with different reader needs in mind.
